# 审计账本 #3：身份证 OCR 长事务专项审查

## 结论

继续保持 `OPEN`。本轮只检查代码事务边界和超时配置，没有对真实 OCR 服务做时序压测，没有改动旧身份证影印本流程，也没有用 S3 新异步路径冒充已修复证据。

## 现有路径

`PersonIdCardImageService.uploadAndRecognize` 在公共方法入口标有 `@Transactional`。同一事务覆盖上传文件写盘及 SHA-256、按 SHA 查询去重、草稿行插入/冲突处理、同步 HTTP OCR、OCR 结果或失败状态写入、操作审计与返回。除 `skipOcr=true` 外，方法调用 `ocrClient.recognize(file.getBytes(), file.getContentType())` 后才提交主事务。

`PaddleOcrHttpClient` 使用 `IdCardOcrProperties.timeoutMs` 设置连接/读取超时；默认由 `IDCARD_OCR_TIMEOUT_MS` 映射为 15000 ms。数据库事务因此可能至少跨越一次接近 15 秒的外部等待，另有数据库、文件和审计耗时。此代码路径确属外部调用位于长事务中的结构性风险；本轮没有压测数据，不报告实际锁持有分布或生产影响。

## 文件和数据库部分失败风险

本地文件写入不受 Spring 数据库事务管理。代码会在草稿 insert 失败或 SHA 唯一键冲突时尝试删掉刚写的对象；删除错误可能留下孤儿文件。相反，事务提交失败时，数据库草稿变更会回滚，但已成功的物理文件不自动回滚，形成 DB/文件非原子边界。OCR 失败会在同一主事务里写 `FAILED` 并返回记录，但如果随后数据库提交失败，文件和 OCR 副作用均不会回滚；审计子方法标有 `REQUIRES_NEW`，但调用由同一 bean 内部直接发生，Spring 代理不拦截 self-invocation，因此不能将其视为可靠的独立提交保证。

这些是从当前代码/事务代理语义审查得出的风险，不代表已复现的特定线上故障。

## S3 能复用什么

S3 提供私有文件对象键、owner 快照、SHA-256、材料状态、数据库任务和关联表、Outbox、有限 worker、租约、幂等、审计与结果校验，可供 S4 设计异步 OCR 任务时作为模型参考。它当前只接受 `MIGRATION_IN` 预审材料并使用显式标记的 Mock；没有将身份证影印本上传/识别入口切到 S3，也没有真实 Python 或 OCR 服务联调。因此旧入口仍同步识别，审计 #3 继续 OPEN。

## 最小修复方向（尚未实施）

可由 S4/S 后续变更单独验证的最小方向：第一事务仅校验 owner、持久化上传草稿及 `OCR_PENDING`/任务和 Outbox；提交后由有界 worker 读取私有文件并调用 OCR；第二事务以状态/version 条件写结果或安全错误并完成审计。需要定义幂等请求、文件补偿/孤儿回收、任务轮询/取消、敏感字段最小化、HTTP 超时与租约配合，并对迟到 worker 做 CAS 防护。该建议没有覆盖和改写当前传统入口，未经独立实现及长事务回归不得更改审计状态。
