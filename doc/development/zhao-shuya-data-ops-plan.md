# 赵书亚：数据与部署运维实施规划

编制日期：2026-11-08。依据《邑循项目详细分工与协作计划》及当前仓库的静态检查。

本文是实施建议，不表示相关功能已部署或通过验收；本次未启动服务、执行数据库变更或运行测试。团队尚未提供最终截止日期，以下按从实际启动日起约 4 周、20 个工作日、每天 4—5 小时估算，总投入约 80—100 小时；包含联调和返工，课程周次按团队实际进度映射。

## 1. 你的完成目标

交付一套可重复部署、可验证数据一致性、可测量性能、可定位故障的运行环境，覆盖：Redis、MySQL 主从与读写路由、Nginx 双业务实例、Docker Compose、日志与指标、压测与恢复演练。RabbitMQ 环境和监控也归你集成，消息业务逻辑由张锦源负责。

建议顺序：基线和可观测字段 → 最小容器环境 → Redis → 主从和读写路由 → 双实例一致性 → 压测、故障恢复和报告。每次只引入一种主要变化，运行同一套业务回归后再推进。

## 2. 仓库起点：复用什么，补什么

- `pom.xml`：Java 17、Spring Boot 3.5.3、普通 MyBatis、Redis、AOP 和 Log4j2 已存在。本次检查未见 Actuator/Micrometer 依赖。
- `src/main/resources/application.properties`：目前是单数据源，Redis 默认关闭；上传与导出路径已有环境变量。
- `cache/OptionalRedisService.java`：已有 JSON 缓存、TTL、异常回源封装；需增加命中/未命中/异常指标，核对故障超时；现有按模式失效使用 `keys(pattern)`，应评估改成精确键或版本键。
- `stats/UnifiedStatisticsService.java`：统计 Key 已含数据范围、地区、部门、日期及查询参数，应复用并补充跨角色测试，不能当作从零实现。
- `security/TokenRevocationService.java`：同时使用 Redis 和进程内撤销表。Redis 故障时，实例 A 注销后的本地状态无法自动同步到 B，需与张锦源一起修复和验证。
- `src/main/resources/log4j2-spring.xml`：已有滚动文件日志；当前日志模式未体现统一 traceId、taskId、instanceId。
- `config/nginx.population.conf.example`：已有静态资源与单实例 API 代理示例，需扩展双实例、超时、日志及压缩配置。
- 仓库文件检索未见 Dockerfile、Compose 或读写路由实现；既有数据库验证、全栈验证脚本和迁移脚本可复用。

以上仅为静态检查结果；既有测试报告不能替代本次集成环境复验。

## 3. 分阶段安排与完成条件

### 第 1 阶段：第 1—3 天，基线与最小部署

1. 核对 Docker 运行条件、可用内存和磁盘、数据库版本、服务端口、构建命令；记录环境清单。先不锁定未知的 AI 资源配置。
2. 在隔离测试库跑通已有初始化与增量迁移流程，核实 README 中迁移范围描述与实际脚本的差异；保存当前测试结果和已知失败项，和张锦源明确归属。
3. 记录登录、区划、字典、统计、迁入申请/审批/显式执行、上传和导出下载的基线行为。
4. 编写业务服务多阶段 Dockerfile、前端构建/静态服务配置、Compose 和无密钥的 `.env.example`。初版包括主库、单个业务实例、Nginx，随后加入 Redis 和 RabbitMQ。
5. 数据库持久化，应用按环境变量定位上传/导出目录；增加启动检查及连接失败重试。已有库只执行必要的增量脚本，初始化操作与日常启动分离。
6. 从此阶段开始预留 instanceId、traceId 和测量记录，保存单实例、无缓存的基线结果。

完成条件：按文档能构建和启动；前端经 Nginx 调用 API；上传与导出在重启后可用；失败项有记录。

### 第 2 阶段：第 4—6 天，Redis 深化

1. 复核区划、字典、统计的缓存键、TTL、更新入口、事务提交后失效和权限范围。统计明确允许陈旧的窗口；必须即时一致的查询绕过缓存。
2. 字典/区划优先使用精确 Key 失效；统计可采用命名空间版本键等可控方案，避免将大范围扫描作为正常写入路径。补测并发读写期间失效效果，不能把删除一次 Key 等同于强一致。
3. 增加命中、未命中、Redis 错误和回源耗时指标。区分“关闭”“未命中”“故障”，避免把 Redis 故障误计为正常 miss。
4. 与张锦源确定 JWT 撤销的共享事实来源。建议撤销先持久化主库，Redis 作为加速层；Redis 不可用时校验回主库。撤销记录持久化失败不能返回注销成功。缓存回源与安全撤销使用不同故障策略。
5. 测试命中、过期、更新失效、不同数据范围隔离、Redis 停机/恢复，以及故障期间 A 注销、B 拒绝旧 Token。重启实例后再次验证撤销状态。

完成条件：业务读取可回源、结果正确；跨实例撤销有可复现证据。仅有单实例本地撤销成功不足以验收。

### 第 3 阶段：第 7—10 天，主从与读写分离

1. 统一主从数据库版本，在隔离环境配置复制账号、主从唯一标识、复制配置和从库只读。已有数据从一致性快照初始化复制，避免独立导入两份演示数据后直接宣称复制正确。
2. 先验证复制，再接应用路由。保留单库配置模式，便于本地开发、对照和定位问题。
3. 默认走主库，仅对与张锦源核定的可延迟查询开放从库：首轮选统计趋势、区划/字典查询等。不能把所有 GET 或所有 `readOnly=true` 方法自动路由从库。
4. 写事务、审批/执行校验、权限和撤销查询、文件授权查询、锁定读取、写后立即查询固定主库；同一写事务内不切换库。核对路由发生在获取连接之前，检查嵌套调用和上下文清理。
5. 记录主/从路由日志或计数。独立观察复制状态、最后错误、应用延迟探针与从库连通性；不能仅靠单个延迟数值判断可用。
6. 先采用从库异常时只读请求受控回主策略，限制并发/连接预算，避免故障将主库压垮。主库故障明确报错，本轮不承诺自动主从切换。
7. 注入暂停复制、从库停机等场景，验证延迟查询可陈旧、强一致流程读主、恢复后复制追平。缓存验证和从库验证分别运行，避免缓存掩盖实际数据源。

完成条件：具备复制证据、实际路由证据、复制延迟与回主证据；迁入审批和执行回归通过。

### 第 4 阶段：第 11—13 天，双实例与模块集成

1. 两个业务容器复用镜像，分别设置 instanceId，共享 JWT 配置、数据库和 Redis。Nginx upstream 指向两个实例，访问日志记录 upstream、状态与耗时。
2. 两实例挂载同一上传/导出持久卷。验收“经 A 上传、经 B 下载”和相反方向；客户端仍通过 Java 权限校验获取文件。
3. 核查内存中的业务状态、限流/撤销状态及定时任务。导出清理、证件过期等任务在双实例下须证明幂等或单执行；必要时独立调度实例，不以粘性会话掩盖共享状态问题。
4. 配置连接和读取超时，记录单实例停机后的实际失败窗口。写请求不配置无条件跨实例重放；重试与业务幂等由张锦源共同核对。
5. 集成 RabbitMQ 的持久卷、账号、健康检查和指标。队列声明、确认、重试、死信和幂等实现由张锦源负责。
6. 拿到王家兴的依赖、模型/索引挂载、端口和健康检查后集成 AI 服务；统计/RMI 服务同样由模块负责人提供构建与运行契约。使用 Compose profile 区分核心环境和可选服务。
7. 与张蕊核对 SPA 路由、API 路径、Gzip、带内容哈希静态资源缓存和入口 HTML 更新策略。

完成条件：两个实例均有业务请求记录；一个停止后可继续服务；文件、注销及任务状态一致；各服务持久化和重启行为有记录。

### 第 5 阶段：第 14—16 天，日志、指标与规则诊断

1. 贯通请求 traceId、异步 taskId、instanceId、接口、耗时、状态与错误分类；异步线程显式传播上下文，不记录材料正文、完整证件和 Token。
2. 接入受保护的运行指标：请求 P50/P95/吞吐/错误率、JVM/CPU/内存、连接池等待和占用、缓存命中率、复制状态及延迟、队列 ready/unacked 和任务耗时。
3. 首版采用受保护的聚合指标接口、规则配置和诊断脚本；是否增加 Prometheus/Grafana 随演示需求决定，避免监控平台占用主要开发时间。
4. 完成至少三条可核查规则：连接池等待与慢 SQL、Redis 异常与回源增多、从库复制异常与路由回主。阈值先按基线设定，记录窗口与持续时间，避免写死没有依据的结论。
5. 输出诊断记录：异常指标和时间窗口 → 对应日志/traceId → 可能原因 → 建议检查项 → 恢复验证；对证据不足的原因标明待核实。
6. 给张蕊提供聚合接口字段、单位、采样窗口与失败语义，由她实现 ECharts/JavaFX 展示。浏览器不直连中间件管理端口。

完成条件：注入一次故障后，能用指标发现、用日志定位，并在恢复后看到指标恢复。

### 第 6 阶段：第 17—20 天，实验、恢复与交付

1. 压测首轮统一采用一种工具，例如团队熟悉的 JMeter；保存脚本、虚构数据、账号/权限范围、预热、并发、持续时间和原始输出。
2. 建议起始负载：10/30/60 并发，每组预热 1 分钟、正式 3—5 分钟、重复 3 次，按硬件能力调整；这些是实验建议，不是吞吐承诺。
3. 缓存对照：同一实例、同一数据集，缓存关闭/冷缓存/热缓存；读写路由对照：缓存关闭，单库/主从；负载均衡对照：其他设置一致，单实例/双实例。标明同机双实例共享 CPU 和数据库资源的限制。
4. 至少测统计查询、带权限的分页查询、迁入办理混合流程。读取接口既检查 HTTP 状态，也检查数据范围与字段；审批/执行等写场景使用隔离数据和可控的唯一标识。
5. 保存 P50/P95、实际吞吐、错误率、CPU/内存、SQL/连接池数据；按证据选择一个瓶颈优化并复测，例如慢 SQL 的 EXPLAIN/索引。不要同时改很多因素后归因。
6. 演练业务实例停机、Redis 停机、从库暂停复制；至少一个场景形成完整时间线：注入、发现、定位、恢复、验证和复盘。
7. 备份数据库、上传/导出文件及必要配置元数据，在新的隔离库/卷中恢复；协调数据库与文件备份时点，核对记录数、抽样文件哈希与业务查询。AI 索引区分备份与可重建，模型和知识库版本需可追溯。
8. 完成干净环境启动验证、部署手册、备份恢复手册、实验报告和个人答辩脚本。没有云主机或远程验证时，状态写为本地 Compose 验收。

完成条件：他人按文档可启动；备份实际恢复成功；性能结论有原始数据；五项主责均有正常与故障证据。

## 4. 协作输入：尽早拿到这些信息

- 张锦源：确认可走从库的查询白名单；事务与强一致读取清单；JWT 撤销持久化方案；双实例定时任务处理；业务/统计服务构建参数；MQ 连接需求、队列和任务状态契约。公共依赖、数据库迁移和安全模块修改先同步。
- 王家兴：提供 AI 服务构建命令、锁定依赖、健康检查、CPU/内存/GPU需求、模型下载和挂载、索引持久化与重建方式、超时与降级行为。AI 尚未就绪时，核心环境可先独立验收，并如实标记集成未完成。
- 张蕊：提供前端构建产物和路径约定；你提供 Nginx 配置及受保护的运维聚合数据；共同核对压缩、资源缓存和浏览器页面加载结果。
- 团队共同确认：最终验收时间、硬件/云主机条件、教师对 Redis/MemCached 和云化部署的具体口径。未确认前继续可独立完成的基础工作。

## 5. 建议新增文件及提交拆分

路径为建议，实施时再创建；遵循现有 `doc/`、`config/`、`scripts/` 目录习惯。

1. `config/docker/` 下的 Dockerfile、`compose.yaml`、环境变量示例与初始化说明：最小环境提交。
2. Redis 指标、键策略与验收脚本：缓存提交；JWT 共享撤销修复单独提交并由张锦源复核。
3. 主从配置、数据源路由、业务白名单与集成验证：先复制环境、后应用路由两个提交。
4. `config/nginx/` 双实例配置、共享卷与实例标识：双实例提交。
5. 日志上下文、指标及 `scripts/ops/` 诊断脚本：可观测性提交。
6. `scripts/perf/` 压测脚本、`doc/testing/` 数据与故障报告、`doc/deployment/` 部署恢复手册：验收提交。

每项证据至少记录：代码提交、环境版本、数据规模、执行命令、预期、实际、原始结果位置、已知限制。测试结果按实际填写。

## 7. 个人答辩建议：约 8 分钟

1. 1 分钟解释运行拓扑和数据事实来源。
2. 1 分钟演示 Redis 命中、失效与故障回源，并说明安全撤销为何另设一致性方案。
3. 2 分钟展示主从复制、实际路由和延迟下强一致流程。
4. 1 分钟展示双实例分流、文件访问和停机后的行为。
5. 2 分钟展示性能对照及一次故障的证据与恢复过程。
6. 1 分钟说明一键部署、备份恢复和已知限制。

最容易被追问的点：从库延迟怎么办、Redis 故障时注销是否仍有效、两个实例如何共享文件和任务状态、定时任务是否重复执行、性能提升是否来自公平对照。
