## #64：真实 Redis 与双 JVM

旧实现已有本地定时清理、严格共享模式和故障时拒绝访问，既有测试大多使用模拟 Redis。本轮采用社区构建的 Redis for Windows 8.10.3（非 Redis 官方 Windows 发行版），下载包 SHA256 与发布资产声明一致；隔离目录及数据、配置和日志保留在本机。仅监听 127.0.0.1，独立随机端口、随机凭据、唯一 key 前缀，两个独立 JVM 分别使用内存 H2；没有使用团队 Redis 或现有数据。RDB 自动保存关闭，测试中执行显式 SAVE，AOF 关闭。测试使用 HTTP `/api/auth/login`、`/api/auth/me` 和 `/api/auth/logout`。

本轮实测：A 登录的令牌在 B 可用；A 注销后 A、B 均返回 401，B 连续查询五次仍为 401；另一个用户的令牌和不同 JTI 的新令牌均可用。Redis 标记的 PEXPIRETIME 与 JWT 的绝对 exp 一致。Redis 不可用时带令牌请求返回 503、新登录被拒绝、无令牌健康检查返回 200；对应用 ACL 禁止 SET 后注销返回 503。检查的故障响应没有出现本轮 Redis 凭据或环回地址。

保存 RDB 后正常关闭 Redis，再使用同一数据目录启动：最初认证请求返回 503，客户端重连后两实例均以 401 拒绝旧令牌；应用 A/B 再重启后也为 401。这只证明本次显式保存成功的重启，不能证明异常宕机、故障切换或所有已确认写入均持久化。

**RED：** 换用独立空数据目录模拟数据丢失，原先已确认吊销且 JWT 尚未到期的令牌在 B 返回 200。这是共享吊销标记丢失后无法识别已撤销令牌的真实风险；该场景未访问或修改生产 Redis。恢复后的正常认证可用不等于安全恢复。真实环境中的并发读写、严格模式本地映射完全不参与的动态注入、自动过期等待等尚未全部单独表征；已有单元/模拟回归不能替代它们。

建议先评审 Redis 持久化、复制、备份、恢复与故障切换的确认写入丢失窗口；评估持久吊销记录、用户/会话代际或安全恢复期间统一失效机制，明确多实例一致性和可用性权衡。生产验收须覆盖异常终止、丢数据、恢复、全实例重启及有效期内旧令牌拒绝，并证明写入确认与恢复边界。架构决策前不得将 #64 标为 FIXED_VERIFIED；本轮无架构修改。

## #29：来源追溯

以下代码判断与实际表征分开：

- 最后成员迁出：`MigrationService.executeOut` 锁定家庭户并读取 `headPersonId`，归档人员户籍后将成员置 LEFT，再 `markHouseholdPending` 清空指针。原户主 ID 在清空前可读；户籍归档保存的是迁出人员的姓名和 ID，不能无条件证明其为历史户主或证明所有时点姓名。最后成员无户主也可进入待销户。
- 最后户主注销：`CancellationService.executePerson` 读取当前人员及户主指针，存在户籍时先写人员户籍归档，再将成员置 CANCELLED 并清空户主指针。人员注销草稿姓名为草稿时点快照，户籍归档姓名为归档时当前人员姓名；二者时点不同。本轮 H2 真实业务链路证明该路径后续家庭户归档的户主 ID 和姓名都为空，人员户籍归档和审批执行记录仍存在。
- 原本无户主、最后非户主迁出：迁出服务允许户主指针和有效 HEAD 均为空；最后成员直接离户路径也要求指针为空并满足无成员、户籍和在途迁入等约束。无法仅由空指针推断历史从未有过户主。
- 最后非户主人员注销：当前 `executePerson` 只有注销人员等于户主指针时才调用 `markPending`；因此无户主的最后非户主注销并不能由此代码推断必然进入待销户。此差异是静态发现，尚未另做动态验证。
- 户主变更会把旧成员关系改为 OTHER、新成员改为 HEAD；日志调用包含原因，当前代码并未建立可证明完整历史的户主姓名事件快照。历史成员关系、现有人员姓名、迁出/注销申请和审批轨迹可能提供线索，但不足以普遍证明唯一原户主及该历史时点姓名。历史异常无户主家庭户尤其不能自动回填。

家庭户销户时 `houseTarget` 按当前 `household.head_person_id` 关联人员，`insertHouseholdArchive` 直接写当前目标中的 ID 和姓名。因此相同 NULL 既可能表示从未有户主，也可能表示旧指针被清空且历史信息丢失。此次新增测试只覆盖最后户主人员注销到家庭户归档这一条完整链路；迁出后最终销户、重复变更户主、历史成员、无户主及归档列表/详情等组合尚需独立动态表征，不应视为已完整关闭。

未来方案应在清空前同一事务中记录事件型快照，包含家庭户 ID、原户主 ID、事件时可信姓名、事件类型及来源、时间、关联业务申请；对无户主、未知/历史不可恢复使用不同显式状态。应以业务事件唯一键或等效约束防重，配合家庭户锁/版本检查、事务回滚和并发测试；不得用新姓名或任意历史 HEAD 猜测回填。直接离户可能没有业务申请，来源建模需显式支持对应操作事件。具体 Schema 和迁移需先完成数据来源证明、历史不可恢复比例评估、产品语义及审批，不在本轮施工。
