# 邑循项目详细分工与协作计划

> **项目全称：邑循——基于检索增强生成与多模态文档理解的人口治理平台**  
> **团队成员：张锦源、赵书亚、张蕊、王家兴**  
> **编制日期：2026 年 11 月 1 日**  
> **文档用途：任务分配、接口协作、进度跟踪、课程验收和答辩准备。**

人员主责以团队已确定的分工为准；具体实现方案、评测规模和排期为建议，需随实际开发进展维护。本文描述的待完成事项不代表已经实现。

## 一、项目目标与实施原则

### 1.1 项目目标

基于现有人口管理系统，完成课程要求的分布式改造、软件质量提升、UI 优化和智能运维，并完善 RAG 政策问答、多模态文档理解和智能办理辅助三项创新，形成可以独立部署、完整演示、定量评测的项目。

### 1.2 实施原则

1. **先稳定，再扩展。** 先理解并修复现有系统问题，再加入分布式机制和 AI 能力。
2. **保留既有技术栈。** 继续使用 Spring Boot、普通 MyBatis、MySQL、Vue 3、Element Plus 和 ECharts，AI 能力通过独立 Python 服务接入。
3. **课程要求有落点。** RMI、消息队列、缓存、读写分离、负载均衡等必须有代码、运行场景和验收证据。
4. **创新形成闭环。** 政策问答、材料预审、办理辅助围绕同一业务场景联动，避免成为互不关联的演示模块。
5. **主责明确，协作分担。** 每项任务确定一名主责人，协作人负责明确的输入或配套工作。
6. **四人均承担代码、测试、文档和答辩。** 不将联调、测试或报告全部交给某一个人。

### 1.3 首轮共同业务场景

以“户籍迁入”为首轮完整场景：

```text
用户描述迁入需求
    ↓
RAG 检索办理指南，展示政策依据与材料清单
    ↓
用户上传身份证、户口簿和申请表等模拟材料
    ↓
异步材料预审，提取字段并标出缺失、低置信度和跨材料冲突
    ↓
用户核对、修正并确认信息
    ↓
生成申请草稿
    ↓
按既有权限进行提交、审批和显式业务执行
```

AI 首轮辅助到草稿阶段，不能自行审批、执行迁入或改写正式人口主档。

## 三、张锦源：后端与业务编排

### 3.1 后端维护与 Bug 修复

- 梳理 Controller、Service、Mapper、DTO/VO、权限和数据库字段之间的关系。
- 整理问题清单，区分业务缺陷、测试断言过期、测试数据冲突和环境问题。
- 优先核实并处理当前已发现的 viewer 数据范围、导出下载权限断言及测试身份证号重复问题。不能只修改断言使其通过，应先明确业务契约。
- 回归登录、人口信息、家庭户、迁移、申请、审批、执行、材料和导出等关键路径。
- 完善参数校验、异常响应、事务回滚、版本冲突和重复操作处理。
- 维护已有“审批通过后仍需显式执行”的规则。

**验收：** 修复项有复现方式、原因、改动和回归用例；未解决问题明确记录；核心业务不因新技术接入而回归。

### 3.2 RMI、反射与动态代理

- 建议抽取小型统计计算服务，定义远程接口、可序列化 DTO、服务端和调用端。
- 在两个独立 JVM/进程之间完成调用，避免把普通本地方法调用当成 RMI 演示。
- 使用 Java 反射与动态代理统一记录方法、耗时和异常，说明其与业务实现的分离关系。
- 远端不可用时返回明确错误或受控降级结果。
- 聚合计算尽量使用聚合 DTO，不将完整人口敏感档案传入演示服务。

**验收：** 独立进程调用成功；可以演示远端关闭后的行为；代理日志能与具体调用对应。

### 3.3 RabbitMQ 异步任务与多线程

- 负责业务端生产者、消费者、任务状态、结果持久化与查询接口。
- 首轮选择“材料预审”作为异步场景，导出异步化按剩余工作量安排。
- 任务具有唯一 ID、幂等键、创建人、业务类型、状态、结果引用和失败原因。
- 使用有界消费者并发或线程池，避免无限创建线程。
- 配置消息确认、有限重试和死信处理；重复投递不能重复产生业务结果。
- 任务与发件事件先持久化，再可靠发送；不将一次 `send()` 调用等同于端到端可靠处理。
- 调用王家兴的 AI 服务，保存结果后更新任务状态；识别失败不自动改写业务主档。

**边界：** 赵书亚负责 RabbitMQ 实例、连接配置、持久化和监控；张锦源负责消息业务逻辑；王家兴负责推理处理。

**验收：** 创建任务后可查询状态；成功、失败、重试、消费者中断和重复消息均有测试记录。

### 3.4 Web Service 服务化

- 先确认教师对 Web Service 的具体形式要求。
- 保守方案为统计服务增加最小 SOAP/WSDL 适配，复用同一统计逻辑。
- 提供服务描述、请求/响应示例、独立客户端和异常示例。
- 原有 REST 接口继续服务 Web 前端，不为课程演示重写业务接口。

**验收：** 可查看服务描述并独立调用；不能仅以已有 REST 接口宣称完成课件中可能单独要求的 Web Service。

### 3.5 智能办理的业务编排

- 与王家兴共同约定事项、材料、证据、清单和建议动作的数据结构。
- 负责后端办理状态机、工具白名单、当前用户权限校验和草稿创建。
- 任何写操作以后端校验为准，不信任模型返回的用户身份、权限、材料所有权或审批结论。
- 人工确认请求要有业务状态和幂等校验，重复点击不能生成多份草稿。
- 保留调用轨迹，支持定位失败步骤。

**验收：** 事项确认到草稿可完整走通；未确认、无权限、状态不合法时拒绝写入；不绕过既有审批流程。

### 3.6 张锦源交付物

- 后端缺陷清单与修复记录。
- 后端接口契约、任务状态模型及消息字段说明。
- RMI、反射/动态代理和 Web Service 示例及运行证据。
- 异步任务、工作流、权限、事务与幂等代码和测试。
- 后端架构、分布式改造与业务编排报告章节。

## 四、赵书亚：数据与部署运维

### 4.1 Redis 缓存

- 深化已有可选 Redis 能力，优先缓存区划、字典和适合缓存的统计聚合。
- 明确缓存 Key、TTL、更新失效、权限范围和版本策略。
- 对用户可见范围不同的统计，缓存键包含必要的范围信息，不能复用成全量结果。
- Redis 关闭或不可用时回源 MySQL，不能让人口业务整体不可用。
- 记录缓存命中情况和相同负载下的性能对比。

**验收：** 命中、过期、更新失效、故障回源均可演示；结果与数据库一致。

### 4.2 MySQL 读写分离

- 统一集成环境数据库版本，建立主从复制，维护初始化、复制配置和验证步骤。
- 主责数据源和读写路由机制，与张锦源核对事务边界、Mapper 和接口归属。
- 写事务、审批/执行校验、写后即时查询走主库；允许短暂延迟的查询和统计可走从库。
- 从库延迟、不可用时明确回主或失败策略；不得将“配置两个连接”直接当作读写分离完成。
- 分析慢 SQL、索引和连接池，并记录变更依据。

**验收：** 有复制状态、实际路由和延迟测试证据；核心业务不因读到旧状态而出错。

### 4.3 Nginx 双实例与负载均衡

- 配置统一入口、静态资源和 `/api` 反向代理。
- 启动两个业务服务实例，配置 upstream，并通过日志或实例标记验证分流。
- 与张锦源共同验证 JWT 配置、退出撤销状态、任务状态和文件访问的一致性。
- 同机演示可使用共享持久卷；材料和导出文件必须能从任一实例访问。
- 关闭一个实例后验证请求仍能通过可用实例处理，记录失败窗口和恢复行为。

**验收：** 双实例均收到请求；单实例故障后可继续访问；不能以仅启动一个实例作为负载均衡证据。

### 4.4 Docker 与部署

- 主责 Docker Compose、网络、卷、启动依赖、健康检查和配置模板。
- 张锦源、王家兴、张蕊分别提供自身模块的构建命令、依赖、端口和运行参数，赵书亚负责集成。
- 部署业务服务、统计服务、AI 服务以及所需中间件，避免将无关组件全部引入。
- 数据库、上传文件、导出文件和索引按生命周期持久化。
- 提供首次初始化、日常启停、升级、备份恢复与故障排查说明。
- 有云主机时完成远程部署；仅本地 Compose 跑通时如实标注，不写“已上云”。

**验收：** 按说明可在干净环境构建和启动；重启后必要数据保留；依赖和资源条件明确。

### 4.5 日志、智能运维与性能优化

- 统一 Log4j2 日志字段，与各服务贯通 traceId、taskId、实例标识和错误分类。
- 结合 Actuator/Micrometer 等指标采集方式观察请求延迟、错误率、数据库连接、队列积压和资源使用。
- 实现基于阈值和规则的诊断，至少关联“异常指标、对应日志、可能原因、建议检查项”。
- 对缓存、数据库和负载均衡进行前后对比，记录 P50/P95、吞吐量、错误率、CPU/内存及测试配置。
- 选择至少一个故障场景，完成注入、发现、定位、恢复和复盘。
- 与张蕊共同完成 Gzip、静态资源缓存等传输优化：张蕊负责构建产物，赵书亚负责 Nginx 配置。

**验收：** 有可复现实验和真实测量；不能只展示日志列表或没有观测依据的 AI 诊断文字。

### 4.6 赵书亚交付物

- Redis 策略、主从复制与读写路由配置及验证记录。
- Nginx 双实例配置、Docker Compose 和环境变量模板。
- 部署、备份恢复和运维手册。
- 压测脚本、原始结果、性能对比与故障演练报告。
- 数据优化、部署和智能运维报告章节。

## 六、王家兴：技术优化与创新

### 6.1 AI 服务基础

- 使用独立 Python 服务承载推理与检索，优先通过 HTTP 与现有 Java 服务连接。
- 提供依赖锁定、模型/索引版本、启动说明、健康检查、超时与错误结构。
- 保留不使用大模型时的降级模式，模型失败不影响普通业务办理。
- 设计结构化结果并与张锦源、张蕊冻结字段；不让前端直接拼接或解析模型自由文本来执行业务。
- 向赵书亚提供构建命令、模型下载/挂载方式、资源需求和容器运行参数。

### 6.2 创新一：基于混合检索与重排序的 RAG 政策问答

1. 梳理已有 Markdown 知识库，补充来源、适用地区、版本、生效/失效日期。
2. 保留现有中文二元组 BM25 风格检索作为基线。
3. 增加语义向量检索、结果融合和重排序，初期可采用 BGE 系列模型及可持久化的本地索引。
4. 针对多轮问题进行必要的独立问题改写，检索前考虑地区和有效版本。
5. 约束答案引用检索证据；没有足够依据时明确说明，不能编造政策。
6. 输出答案、引用片段、来源版本、当前模式和耗时；检索分数不直接宣称为答案正确概率。
7. 与张蕊共同检查引用是否可读、可展开、可追溯。

**建议评测集：** 至少 80 条带标准证据的问题，其中保留独立测试部分，覆盖迁入、居住证、材料不全、过期政策、无依据和多轮追问；数量为计划建议，非现有成果。

**对照实验：** 现有检索 → 混合检索 → 混合检索＋重排序。

**指标：** Recall@5、答案正确率、引用支持率、无依据问题拒答表现及 P95 延迟。

### 6.3 创新二：基于文档理解与规则融合的材料预审

1. 接通现有 OCR 适配接口，首轮支持身份证、户口簿、申请表三类模拟材料。
2. 实现或接入材料类型识别、方向修正、模糊提示、版面分析和字段抽取。
3. 返回字段值、来源材料、页码、位置和可用的置信度，支持原图对照。
4. 根据办理事项核对材料完整性及跨材料字段；区分冲突、识别不确定和规则不适用。
5. 不把 OCR 错字或低置信度直接判为造假；结果提供人工核对和修正入口。
6. 对图片、扫描 PDF 等输入建立一致的处理流程和明确的失败返回。
7. 与张锦源对接异步任务，不由 AI 服务自行审批或修改业务主档。

**建议样本：** 与张蕊共同整理至少 40 组虚构材料，涵盖清晰、旋转、模糊、缺页和字段冲突；区分开发与测试样本。

**对照实验：** 人工录入 → OCR 回填 → OCR＋规则核验。

**指标：** 字段准确率/F1、冲突检出率、误报率、人工修正量及完成时间。明确模拟材料的效果边界，不直接宣称真实业务泛化能力。

### 6.4 创新三：基于受控工具调用的智能办理辅助

- 完善事项识别、问题补全、政策检索、材料核验和清单生成策略。
- 为张锦源提供结构化建议动作及其依据，定义每种动作的必要输入、前置条件和失败情况。
- 与张锦源共同明确工具白名单和人工确认点；业务权限、状态变更、草稿写入由后端负责。
- 与张蕊共同设计“识别—解释—修正—确认”的交互，不将所有步骤压在一个聊天回复中。
- 保留现有规则式助手作为基线，不默认引入复杂 Agent 框架或自主写库能力。
- 准备信息齐全、材料缺失、模型不可用、政策无依据、越权、重复确认和恢复等场景。

**建议验收：** 至少 15 个端到端场景；统计任务完成率、错误填写率、操作步数、重复草稿数量和非法操作拦截情况。

### 6.5 创新工作边界与优先级

- 首轮优先顺序：可溯源 RAG → 三类材料预审 → 受控办理辅助。
- 先形成可运行的服务与基线，再改进检索、识别和规则，不优先训练大模型。
- 知识图谱、人口趋势预测、大范围模型微调和多 Agent 自主执行暂不列入本轮必交付。
- 项目侧重业务应用与工程创新，若没有方法改进与严谨对照实验，不宣称原创算法创新。

### 6.6 王家兴交付物

- AI 服务、接口说明、模型/索引/知识库版本清单和部署配套资料。
- RAG 检索、重排序、生成和引用链路。
- 文档解析、字段抽取、材料规则核验及结构化输出。
- 办理辅助策略、工具契约和场景集。
- 评测样本、实验脚本、原始结果、消融对比和算法/创新报告章节。

### 7.2 建议接口

下列路径为拟议接口，开发前需核对既有接口并冻结契约，不代表当前已存在。

| 调用方向 | 建议接口/消息 | 核心约定 |
| --- | --- | --- |
| 前端 → Java | `POST /api/ai/tasks` | 提交业务类型、已上传材料 ID 和幂等键；Java 校验材料权限后创建任务 |
| 前端 → Java | `GET /api/ai/tasks/{id}` | 返回状态、进度、结果、冲突和失败原因；只能读取授权任务 |
| Java → Python | `POST /internal/document-analysis` | 使用受控材料引用或文件流；返回类型、字段、位置、置信度、告警及模型版本 |
| Java → Python | `POST /internal/policy-query` | 返回答案、引用、来源版本、模式及耗时；兼容已有问答语义 |
| 生产者 → 消费者 | 材料预审任务消息 | 含 taskId、taskType、traceId、schemaVersion；使用幂等处理和有限重试 |
| 运维 → Web/JavaFX | 受保护的聚合运维接口 | 提供服务健康、延迟、错误率和任务积压，不向客户端直连中间件管理口 |

任务状态建议统一为 `PENDING / RUNNING / SUCCEEDED / FAILED`。人工材料修正属于后续独立业务动作，不通过随意回改任务状态处理。

字段至少明确：类型、是否必填、枚举、时间格式、空值含义、错误码、版本和示例。浏览器统一调用 Java，内部推理服务不承担终端用户业务授权。

### 7.3 数据与文件责任

- MySQL 保存业务事实与任务状态，AI 索引可重建，Redis 缓存可回源。
- AI 输出作为待确认建议，不直接替换正式业务数据。
- 材料、导出文件和任务结果的访问由 Java 校验权限。
- 共享文件卷由赵书亚配置，读写接口由张锦源维护，Python 处理方式由王家兴提供。
- 每次服务调用贯通 traceId，异步场景额外保留 taskId，方便四人联调。
