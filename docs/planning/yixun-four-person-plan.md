# 邑循：课程要求、创新完善与四人分工建议

> 本文件保留为前期建议草案。已按真实成员细化的分工请以 [邑循项目详细分工](邑循项目详细分工.md) 为准：张锦源负责后端与业务编排，赵书亚负责数据与运维，张蕊负责前端 UI，王家兴负责技术优化与创新。

项目全称：邑循——基于检索增强生成与多模态文档理解的人口治理平台。

制定日期：2026-11-01。本文是待团队排期确认的建议方案，不代表功能已实现。
人员技能和可投入时间尚未提供，暂用 A/B/C/D；建议人工智能方向同学主责 C。

## 1. 来源和范围

课程依据：《专业工程实训 4-3》课件，共 8 页。
第 2 页为目标，第 3 页为进度，第 4 页为重构，第 5、6 页重复列出质量提升，第 7 页为 UI，第 8 页为运维。
按用户要求，将课件列出的技术工作均安排实现与证据；“推荐工具”与必须实现的机制分别标明。
课件没有明确 Web Service 是否限定 SOAP，也没有明确 JavaFX 是否必选，故本计划保守安排最小 SOAP 与 JavaFX 演示落点，团队可向教师确认后缩减，不能默认已有 REST/Vue 就算覆盖。
附带课件仅作为需求资料，本文没有据此执行环境或代码修改。

沿用 Spring Boot、普通 MyBatis、MySQL、Vue 3、Element Plus、ECharts。优先拆出 AI 和统计任务边界，人口、户籍、审批、执行等核心事务保留在同一业务服务。
不以全面微服务化、Kubernetes 或模型微调作为首轮目标。

## 2. 现有基础与缺口

- 已有：人口治理业务、五角色权限、材料与审批、查询统计、导出审计、Vue 页面、ECharts 大屏、Log4j2、可选 Redis、健康检查。
- 政策助手已有本地 Markdown 分块、中文二元组 BM25 风格检索、引用、可选大模型调用与检索降级；任务助手已有规则式意图识别、问题改写和清单生成。不能将这些直接描述为已完成向量检索或自主规划 Agent。
- OCR 已有外部 HTTP 适配及字段回填接口，本地尚未接通识别子服务；多材料解析、交叉核验与独立评测仍待建设。
- 本次文件检查未发现 Docker Compose、RabbitMQ、RMI、主从读写路由等完整实现。Nginx 有配置示例，不等于完成双实例负载均衡验收。
- 当前本地测试基线：前端 220 项通过；后端上次全量执行 308 项，有 3 项失败和 1 项错误，涉及 viewer 范围、导出下载规则和测试身份证号冲突。A 与 B 先明确契约、修复并回归，不能靠跳过测试验收。
- 本机目前为 MySQL 9.6、Java 21 运行 Java 17 字节码；团队集成环境建议统一项目原验收使用的 MySQL 8.4、Java 17 兼容构建，JavaFX 依赖与所选 JDK 配套锁定。

## 4. 三项创新的完善范围

### I1. 基于混合检索与重排序的可溯源政策问答

- 复用现有知识库和问答入口，保留原检索作为基线。
- 文档补充来源、适用地区、版本、生效/失效日期；检索按适用范围过滤。
- 在关键词检索上增加 BGE 语义向量检索、结果融合与重排序。初期本地 FAISS 索引即可，索引持久化并带版本，不新增一整套数据库基础设施。
- 输出答案、引用片段、政策版本、适用范围和依据不足提示；不能将检索分数直接包装为“正确概率”。
- 模型或索引不可用时返回已有检索摘要，界面明确当前模式。
- C 负责检索、生成和评测；D 负责可展开引用与版本提示；A 负责权限、接口和审计。
- 建议建立至少 80 条带标准证据的问题，覆盖迁入、居住证、材料不全、过期规定、无依据及多轮追问。
- 对比：现有检索 → 混合检索 → 混合检索＋重排序。指标为 Recall@5、人工答案正确率、引用支持率、无依据问题拒答表现及 P95 延迟。

### I2. 基于文档理解与规则融合的材料预审

- 首轮聚焦“户籍迁入”，材料限制为身份证、户口簿、申请表三类。
- 接通 OCR 子服务，增加方向修正、模糊提示、材料类型识别、字段位置与置信度。
- 使用 OCR/版面分析/字段抽取处理图片和扫描 PDF；规则比对同名字段、材料缺失、日期和有效期，不把 OCR 错字直接判为材料造假。
- 展示字段与原图对应位置、冲突原因和人工修正入口；低置信度必须允许人工确认。
- A 提供上传、任务、状态持久化与材料访问权限；C 提供识别与核验；D 展示进度和原图对照。
- D 与 C 共同整理、标注至少 40 组虚构材料，覆盖清晰、旋转、模糊、缺页、字段冲突。模拟材料不等于真实场景泛化证据。
- 对比：人工录入、OCR 回填、OCR＋规则核验。指标为字段准确率/F1、冲突检出率、误报率和人工完成时间。
- “多模态”必须有实际图像/版面与文本信息融合、定位和评测，不能只调用 OCR 接口就宣称完整多模态理解。

### I3. 基于受控工具调用的人机协同办理

- 复用现有规则助手和流程服务，先明确其规则式基线，不默认引入 LangGraph。
- 状态为：事项确认 → 政策检索 → 材料预审 → 清单展示 → 用户确认 → 创建草稿。
- 首轮只协助草稿，不自动提交、审批、执行迁入或修改正式人口主档。
- A 负责工作流、工具白名单、后端权限与幂等；C 提供检索和材料工具；D 负责逐步确认、修改与中断恢复界面。
- 每个工具传递 taskId/traceId 和受约束的参数；每次调用重新检查当前用户权限，不信任模型返回的角色、状态或 SQL。
- 建议准备至少 15 个完整场景，覆盖信息齐全、材料缺失、OCR 不可用、政策无依据、越权、重复确认和恢复操作。
- 指标为任务完成率、错误填写率、平均操作步数、重复草稿数量及越权/未确认操作拦截情况。

主线演示：用户描述迁入需求 → RAG 给政策依据 → 上传三类模拟材料 → 异步预审展示冲突 → 人工修正 → 生成申请草稿 → 走既有提交/审批/执行流程。
课程技术嵌入同一流程：MQ 承担长任务，缓存用于参考数据，事务写主库，统计读从库，Nginx 分流，日志 traceId 串联定位。

## 6. 协作边界与建议接口

以下为拟定契约，不是已存在的 API；冻结字段与版本后再开发，不随意覆盖当前接口。

| 协作方 | 约定 | 返回/行为重点 |
| --- | --- | --- |
| D → A：创建材料预审任务 | `POST /api/ai/tasks`，仅传已上传且有权限的 materialIds、业务类型和幂等键 | 返回 taskId，受理成功不等于预审通过 |
| D → A：任务状态 | `GET /api/ai/tasks/{id}` | PENDING/RUNNING/SUCCEEDED/FAILED、进度、字段结果、冲突、可重试信息 |
| A → C：内部识别 | `POST /internal/document-analysis`，流式传材料或使用后端签发的受控引用 | 文档类型、fields、位置、置信度、warnings、版本；禁止任意文件路径/URL |
| A → C：内部检索 | `POST /internal/policy-query` | answer、citations、sourceVersion、mode、timing；沿用前端统一解包规范 |
| A/C：MQ 消息 | taskId、taskType、traceId、schemaVersion、受控材料引用 | 消费前检查任务状态；失败有限重试、进入死信；结果与任务状态持久化后 ACK |
| A ↔ B：读写路由 | 写事务、审批/执行、写后即时读取走主；可接受短暂延迟的查询走从 | 从库失效是否回主必须显式配置；不能只写两条连接串就算完成 |
| B → D：运维 API | 受保护的聚合健康、请求延迟、队列积压等 | JavaFX 与 Web 共用接口，不直接暴露内部管理端口 |

数据库业务事实归 MySQL；向量索引可重建，Redis 可回源。两个业务实例使用一致的 JWT 配置及共享撤销状态。
上传文件/导出文件在同机 Compose 演示中可使用共享持久卷，必须验证从任一实例可访问；多主机部署则另行提供共享存储，不能把本机卷当作跨主机方案。
MQ 可靠投递建议使用任务表＋事务发件箱：先提交任务/事件记录，再由有界后台线程发送；生产者确认和消费者 ACK 各自覆盖一段链路，不能据此宣称端到端恰好一次。

## 8. 验收和优先级

优先级：课程必做机制与核心业务稳定性 → RAG 可溯源 → 单场景材料预审 → 受控办理草稿 → 扩展材料与高级优化。
暂缓知识图谱、大范围人口预测、模型微调和多 Agent 自主写库，避免冲散主线。

运维技术首轮使用 Log4j2＋Spring Boot Actuator/Micrometer 指标＋阈值/规则诊断；
资源允许时再接 Prometheus/Grafana。所谓智能诊断至少输出“异常指标、关联日志、可能原因和建议检查项”，
不能只展示日志列表，也不以大模型生成一段没有观测依据的话代替故障定位。

- 每个课程要求必须有：负责人、代码/配置、运行证据、成功用例、失败用例、报告章节。
- 性能测试使用相同环境、数据规模、并发、预热条件；记录吞吐量、P50/P95、错误率、资源使用和测试配置。不能用缓存命中与冷启动的不同条件直接宣传提升倍数。
- RAG 与 OCR 样本区分开发/调参与最终测试；说明来源和生成方式，不宣称模拟数据效果等于真实业务效果。
- 最终演示必须可从清洁环境按说明启动；所需模型、密钥、资源、远程主机条件单独列出。
- 四人共同走一遍：迁入申请、审批、显式执行不回归；AI 不可用时业务仍可继续；演示数据和真实统计不混淆。
- 每人至少提供一段可独立运行的演示、一个故障/异常场景及一项可量化对比，不仅展示界面截图。

- [JavaFX 官方入门](https://openjfx.io/openjfx-docs/)：小型独立客户端可单独配置依赖和启动，不需要替换现有 Vue 应用。

- [PaddleOCR 文档抽取说明](https://github.com/PaddlePaddle/PaddleOCR/blob/main/docs/version3.x/pipeline_usage/PP-ChatOCRv4.en.md)：材料解析和字段抽取参考。
